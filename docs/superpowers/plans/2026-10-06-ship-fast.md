# Ship Fast Implementation Plan

- **Status:** draft
- **Date:** 2026-10-06

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `/ship-fast <spec.md>`, a user-only command that takes a spec
for an hour-sized POC to a tested, smoke-run pull request with green CI, with
no gates, no formal review round and no merge, running independent tasks in
parallel; wire it into `parallel-tasks`, the docs, an ADR and plugin 0.13.0.

**Architecture:** The command is one Markdown file read by the model
(`plugin/commands/ship-fast.md`), pinned by a structure test. It reuses
existing pieces unchanged: `scaffold.py` for new repos, `parallel-plan.py`
and `claude-kit:parallel-tasks` for parallel work, the `code-review` and
`run` skills for quality. Docs and an ADR record the choice. No Python
script changes.

**Tech Stack:** Markdown command and skill files, Python 3.11+ pytest
structure tests, ruff.

**Spec:** `docs/superpowers/specs/2026-10-06-ship-fast-design.md`

## Context for a cold start

- Work in the worktree `.claude/worktrees/ship-fast` (under the repository
  root) on branch `feat/ship-fast`, cut from `origin/main` at `4418d80`. The
  spec and its gate record (`docs/superpowers/gates/2026-10-06-ship-fast-design.md`)
  are committed on this branch. Run every command from the worktree root.
- Setup once per machine: `pip install "markdown~=3.10" "pytest>=8" "ruff~=0.16"`.
- Full checks: `python -m pytest -q`, `ruff check plugin tests`,
  `ruff format --check plugin tests`. Baseline on this branch: all green.
- The plugin is loaded through a junction `~/.claude/skills/claude-kit` →
  the main checkout's `plugin/` (ADR 0005), so the new command becomes
  usable only after the merge reaches local `main`.
- Why (from the spec's Purpose): `/ship` spends most of an hour-sized POC on
  ceremony (two gates, a review round, CI watched three times, merge, main
  verification). `/ship-fast` keeps the checks that catch broken work: TDD on
  the core path, one correctness review, a smoke run against the spec's
  acceptance criteria, green PR CI.
- Decisions already made by the user (do not relitigate): input is a spec
  file and no gate runs; the run ends at an open PR with green CI and the
  user merges; one `code-review low --fix` pass replaces the review round;
  a `**Repo:** new` header scaffolds and creates a private GitHub repo;
  unsettled scope/behaviour/interface/data choices stop and ask; the name is
  `/ship-fast`; branches are `poc/<slug>`; PR CI gets 2 fix attempts.

## Global Constraints

- `plugin/commands/ship-fast.md` must not contain the strings `spec-gate`,
  `plan-gate`, `gh pr merge` or `requesting-code-review` anywhere.
- The command's frontmatter has `disable-model-invocation: true`.
- Plugin version is exactly `0.13.0`; its description contains `/ship-fast`.
- No change to `plugin/commands/ship.md`, `plugin/commands/ship-many.md`,
  the gate skills, or `plugin/scripts/parallel-plan.py`.
- The repo is public: no private repo names or usernames in tracked files.

## Plan questions answered

From the spec gate record's `## Plan questions`:

- **code-review target and the correctness filter** (Task 1, step 6 of the
  command): the target is the branch, `low --fix poc/<slug>`; after it runs,
  every edit that does not fix a correctness bug is reverted before the
  commit.
- **Where the new repo lives** (Task 1, step 1): `scaffold.py` gets no
  `--parent`, so the repo is created beside the other project repos in the
  workspace, like `/new-project`; `<repo>` is the path the script prints.
- **Committing the stack init output** (Task 1, step 1): yes, the init
  output and the spec copy go in one commit before `gh repo create --push`.
- **Handoff cleanup** (Task 1, step 8): cleanup deletes
  `.claude/handoffs/poc_<slug>.md` only by removing the feature worktree it
  lives in; the main checkout's handoff files are left alone.
- **Rerun after a stop** (Task 1, `## Resume`): a rerun resumes: an existing
  `poc/<slug>` worktree skips to step 3, an existing task list skips to
  step 4 and implements only tasks without a commit, and an existing new
  repo with an `origin` remote makes step 1 only fetch.
- **How SC5 runs** (Task 3): before the merge, as a headless `claude -p`
  session told to read and follow this worktree's
  `plugin/commands/ship-fast.md` (the installed plugin serves `main`'s
  files, so the command is not invoked by name); the toy spec is written to
  the session scratchpad, not committed; deleting the toy repo is left to
  the user's confirmation in the `/ship` report.
- **Red first `main` CI on a scaffolded repo** (Task 1, step 1): accepted,
  expected, and stated in the report; it is not a stop.

## Review Focus

- A spec with no `## Success criteria` section but a "Verification" section:
  the command must accept a `##` heading containing "criteria" or
  "verification", not only the exact name.
- A rerun after a stop: the command must not scaffold twice or recreate the
  branch (the `## Resume` section).
- The forbidden strings: a careless "no `spec-gate` runs" sentence would
  break the test; the command says "no gate runs" instead.
- A brand-new repo: the baseline run is skipped, and the red first `main`
  run is reported, not treated as a stop.
- `parallel-tasks` invoked from `/ship-fast`: its text must not claim the plan
  came from `/ship` step 3.

## Git lock retry

Any git command in this repository, in the main checkout or any worktree,
that fails with `Unable to create '...lock': File exists` or
`cannot lock ref` is retried after 5 seconds, up to 5 times. All worktrees
share one `.git` directory, so concurrent worktrees can collide on its locks.
A command still failing after that is handled like any other failed command.

## Resume

A rerun after a stop continues where the last run stopped:

- With `**Repo:** new`, if the repository folder already exists as a git
  repository with an `origin` remote, step 1 only runs `git fetch origin`
  there.
- With `**Repo:** new`, if the repository folder exists as a git
  repository without an `origin` remote (a stop in step 1): skip
  `scaffold.py`, run the stack's init commands only if their output
  (`pyproject.toml` or `package.json`) is missing, commit anything
  uncommitted, then run `gh repo create` as in step 1.
- In both cases above, "the spec" is the copy at
  `docs/superpowers/specs/<spec file name>` in the repository, as after
  step 1.
- If you are already in a worktree on `poc/<slug>`, skip step 2. If
  `git worktree list` shows a worktree on `poc/<slug>`, enter it
  (`EnterWorktree` with its path, or change directory) and skip step 2. If
  only the branch `poc/<slug>` exists, run
  `git worktree add <path> poc/<slug>` (no `-b`) and skip the rest of
  step 2.
- If `docs/superpowers/plans/*-<slug>.md` with `**Status:** fast (ungated)`
  exists on the branch, skip step 3, and in step 4 implement only the tasks
  whose commit message (`<slug>: task N`) is not yet in
  `git log origin/main..HEAD`.

```markdown
# ADR 0021: `/ship-fast` takes a POC spec to a PR with no gates

- **Status:** accepted
- **Date:** 2026-10-06

## Context
`/ship` lands a change on `main` unattended, so it gates the spec and the
plan (ADR 0015, ADR 0016), runs a formal review round, watches CI on the
branch, the PR and `main`, and merges. For a proof of concept of about an
hour, that ceremony takes longer than the POC.

## Decision
- A user-only command `/ship-fast <spec.md>` takes a spec to an open pull
  request with green CI. No gate runs on the spec or its task list; the
  user reviews and merges the PR.
- It writes a short task list (1 to 5 tasks, no step-by-step code) in the
  format `parallel-plan.py` reads, so independent tasks run in parallel
  through `claude-kit:parallel-tasks` (ADR 0017).
- Quality comes from TDD on the core path, a smoke run of the app against
  the spec's acceptance criteria, one `code-review low --fix` pass kept to
  correctness fixes, and green PR CI.
- A spec header `- **Repo:** new <name> <node|python>` scaffolds a new repo
  and creates a private GitHub repo for it.
- A choice the spec does not settle that changes scope, behaviour,
  interface or data stops the run and is asked; smaller "how" choices are
  assumed and listed in the PR.

## Consequences
POCs reach a reviewable PR in far less time, at the cost of unreviewed
specs and plans; the user's PR review and merge is the only gate. Branches
are `poc/<slug>` so POC work is easy to tell from `/ship`'s `feat/`.
`/ship` is unchanged and remains the path for changes that must land
unattended.
```
