# Learning decay: prune stale learnings at ship

- **Status:** approved
- **Date:** 2026-11-15

## Purpose

`claude-kit:capture-learnings` adds to a repo's `CLAUDE.md`, its
`knowledge/` docs and the user's auto-memory at every `/ship` and
`/ship-fast`, and nothing ever takes away. Entries go stale: a command
that changed, a path that moved, a gotcha the feature fixed, a project
memory whose "pending" item is done. A stale entry is worse than none,
because sessions trust it (`conventions/project-memory.md`).

The idea comes from ECC's confidence-scored "instincts" (an external
Claude Code setup; ideas only, no text copied). This change keeps the
goal, not the mechanism: instead of scoring each learning, the step that
writes learnings also prunes the ones the feature made wrong, and the
audits sweep for stale entries in between.

  0046), and its index row

- `conventions/project-memory.md`: the "Capturing learnings" section

  behaviour into an existing flow step).
- Changes to `/ship`, `/ship-fast`, `/ship-many` or the PR body
  reference: they already run capture-learnings and carry its summary.

## Design

### capture-learnings: Prune step

A new step 4, **Prune**, after Route (step 3) and before Harden (today's
step 4, renumbered 5; Write and commit becomes 6, Return becomes 7).
Every cross-reference to a step number inside the file is updated.

**Inputs.** The feature's changed files,
`git diff --name-status origin/main...HEAD` (after the `git fetch origin`
step 2 already runs), including renames and deletions, plus the spec and
plan when present.

**Repo files.** Read the root `CLAUDE.md`, every nested `CLAUDE.md` in a
directory the diff touched (or an ancestor of one), and every
`knowledge/*.md` doc that names a changed, renamed or deleted path, or a
command, script, flag or setting the diff changed. `knowledge/decisions/`
is excluded. For each entry (a bullet, a table row or a short paragraph):

- It names a path the diff deleted or renamed: repoint it to the new
  path, or remove it if the thing is gone.
- It states a command, flag, setting or behaviour the diff changed:
  rewrite it to the new truth, or remove it if the feature made it moot
  (for example, a gotcha the feature fixed).
- Otherwise: leave it alone, even if it looks stale for another reason.
  Prune only acts on what this feature changed.

Edits are terse and imperative, like new entries. A touched
`knowledge/` doc gets `last_updated: <today>`. Prune edits go in the same
`Capture learnings` commit as this run's new entries. A learning routed in
step 3 of this run (written in step 6) is never pruned.

**ADRs.** If the diff contradicts an accepted ADR and the feature added
no ADR that supersedes it, do not edit the ADR: add a summary line
`not written: ADR <NNNN> may be superseded: <why>`.

**Auto-memory.** Only when the session has an auto-memory directory.
Read its `MEMORY.md` and the memory files whose name, description or
body names this repo, the feature's branch, spec, PR, or a skill or
command the diff changed. For each:

- **Project memories** (`type: project`): if this feature resolves an
  open item the memory records (a "pending" check, a next step, a
  deferred item), rewrite the item as done with the date and PR, and
  update its `MEMORY.md` line to match. If the feature contradicts the
  memory's main fact (it describes behaviour this feature removed or
  replaced), rewrite the fact. Delete the file and its `MEMORY.md` line
  only when nothing in it stays true.
- **Feedback and user memories** (`type: feedback`, `type: user`): never
  edit or delete. A code change does not invalidate a preference. If the
  diff seems to conflict with one, add a summary line
  `not written: memory <file> may conflict: <why>`.
- **Reference memories:** rewrite a pointer the diff moved; otherwise
  leave alone.

Memory writes follow the session's memory instructions. Edit by exact
replacement of the lines that change, re-reading the file right before
the edit, never by rewriting the whole file, because `/ship-many`
children may write memory at the same time. Memory writes are not
committed, so the summary lines are the only record.

**Mode.** Prune runs the same with and without `--auto`: repo edits are
reviewed in the PR diff, and memory edits are reported. No approval
pause.

**Filter.** Step 2's filter does not apply to Prune (it decides what to
add, not what to remove). A rerun or resume finds nothing left to prune
in what an earlier run already fixed, so it makes no new edits.

### capture-learnings: summary lines

Step 7 (Return) gains, after the learnings lines and before the
`Hardening:` block:

- `pruned: <file>: <old entry, shortened> → <new entry | removed>` per
  repo edit;
- `memory: <file>: <resolved | rewritten | deleted>: <why>` per memory
  edit;
- the `not written:` lines from this step.

`none` (nothing written) now means no learning written and nothing
pruned. A run that only pruned reports its `pruned:` and `memory:` lines
and no `none`. On a rerun, the existing `already written:` rule also
covers prune edits in the earlier `Capture learnings` commit.

The skill's frontmatter description adds "and prunes entries the
feature made stale".

### Audit staleness check

`plugin/skills/audit/rules.md`, section 4, "Is it built well", gains one
bullet after the CLAUDE.md bullet:

- Stale learnings: in every `knowledge/` doc (not `knowledge/decisions/`;
  `CLAUDE.md` files stay with the CLAUDE.md bullet above, which already
  flags statements stale against the tree and git history), flag paths, commands, scripts, flags and
  settings that do not exist in the tree or that the code contradicts,
  and a `knowledge/` doc whose `last_updated` is older than the last
  commit to a file it describes (`git log -1 --format=%cs -- <path>`),
  marked `inferred (from: git log)`. One finding per doc, listing every
  stale entry under **Impact**.

The audits stay read-only and repo-scoped: they do not read auto-memory.

### ADR

The new ADR records D1 (prune at ship rather than confidence stamps,
with the sweep-only option rejected), D2 (a ship step may edit the
user's auto-memory), D3 (memory deletion rules), D4
(ADRs never edited) and D5 (no memory in audit reports), in the format
of `knowledge/decisions/0000-template.md`. It says that Prune edits are
learnings, not hardening, so ADR 0043's rule that automated runs never
change code or process files on their own still holds.

## Decisions

- **D1. Prune at ship, not confidence stamps.** (User's pick.) Stamps
  cost tokens in every session and depend on sessions noticing that a
  note helped, so useful notes would decay too. Prune runs where
  learnings are already read and written, and only on what the feature
  changed. Rejected: a sweep-only approach (runs only when someone
  audits).
- **D2. Auto-memory is in scope.** (User's pick.) Project memories
  accumulate the most stale "pending" items.
- **D3. Memory deletion only when nothing stays true, and never for
  feedback or user memories.** (My call.) Deletion of an uncommitted
  file cannot be undone; resolving an item in place keeps the history.
  Every memory edit is reported.
- **D4. ADRs are never edited.** (My call.) They record what was decided
  then; a contradiction is reported so the feature (or the user) writes a
  superseding ADR.
- **D5. No memory sweep in the audits.** (My call.) Audit reports are
  written inside the repo, and this kit is public; memory contents must
  not land in a repo file. Between ships, the user can run
  `anthropic-skills:consolidate-memory`.
- **D6. No approval pause, `--auto` or not.** (My call.) Consistent with
  capture-learnings' existing rule ("there is no approval pause"): the PR diff is the review for repo
  edits; the summary is the review for memory edits.
- **D7. Nothing is frozen.** (My call.) The new assertions go into two
  existing test files this change must edit, so freezing them would trip
  `frozen-check.py` on the change itself; the behavioural acceptance
  check (Success criteria 2 and 3) is a manual scenario, not a file.

body):

- It excludes `knowledge/decisions/` and says ADRs are never edited.
- It names `type: feedback` and `type: user` with "never edit or delete".
- It says memory edits use exact replacement and re-read the file.
- The summary names `pruned:` and `memory:`.
- The description mentions pruning.
- `test_harden_step_sits_between_route_and_commit` is updated to the new

## Success criteria

Agreed evaluation and verification criteria:

1. **Suite green:** `pytest` and `ruff check plugin tests`,
   `ruff format --check plugin tests` pass, including the new
   assertions.
2. **Scenario check (manual, in the PR):** in a scratch git repo with a
   `CLAUDE.md` naming `scripts/old.sh` and a gotcha about a bug, a branch
   that renames the script and fixes the bug, and a scratch memory
   directory with a project memory for that repo recording two open
   items, "pending: fix <the bug>" and "first live run pending", plus a
   feedback memory: running the skill (hand mode) repoints the path,
   removes the gotcha, rewrites the "fix <the bug>" item as done with the
   date, and leaves the "first live run pending" item, the feedback
   memory and an untouched `CLAUDE.md` entry unchanged, with matching
   `pruned:` and `memory:` lines. The result is
   pasted in the PR body.
3. **No false prunes:** in the same scenario, `git diff` shows an
   entry about an unchanged file byte-identical.
4. **Post-merge (tracked in memory):** across the next three real
   `/ship` runs, a manual check finds every `pruned:` or `memory:` line
   correct (no wrong removal). One wrong removal means revisiting D3
   or narrowing Prune.
