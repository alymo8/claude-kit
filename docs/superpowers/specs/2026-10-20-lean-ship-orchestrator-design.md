# `/ship` keeps its main session lean

- **Status:** approved
- **Date:** 2026-10-20

## Purpose

A `/ship` run costs most of its tokens in the main session, not in its
subagents. Across 66 past `/ship` runs in this workspace the median run cost
18.0M cost-weighted tokens (input + 1.25 × cache writes + 0.1 × cache reads +
5 × output), of which 16.0M was the main session, and the main session's
median peak context was 391k. (These figures add usage per transcript
record, and Claude Code repeats a message's usage on several records, so they
overstate cost; the post-merge evaluation recomputes the baseline with
`token-report.py --ship` before comparing.) Each of the ~900 turns of a long run re-reads
everything before it, so whatever enters the main context early is paid for
on every later turn. Three things put it there:

1. `/ship` usually runs in the same session as the brainstorming, the spec
   and the spec gate, so 100–180k of design conversation rides along.
2. `/ship` writes the plan (often 40–95 KB, after reading the code it needs)
   in the main session.
3. When every wave has one task, or `parallel-plan.py` fails, `/ship`
   implements the plan inline with `superpowers:executing-plans`, so all the
   code reading, test output and fixing lands in the main session, at a
   context of 360–475k by then.

This change makes the main session coordinate rather than do the work:
`/ship` starts from a fresh session, a subagent writes the plan, and
implementation always runs in subagents through
`superpowers:subagent-driven-development` (SDD). Point 3 is also a quality
change: each task is written in a fresh context and gets SDD's per-task
review, instead of being written late in a 400k+ context.

`/ship-fast` is unchanged (it implements inline on purpose, for speed during
a live demo). `/ship-many` runs each spec as a headless `/ship`, which
already starts fresh, so it inherits points 2 and 3 with no edit of its own.

## Design

### §1 Fresh session for `/ship`

In `spec-gate` step 7, **pass** branch: after the user says yes and the
spec's Status is set to `approved`, the reply confirming it ends with this
line, with the spec's repo-relative path filled in:

> Next: run `/clear`, then `/claude-kit:ship docs/superpowers/specs/<file>`.

When `/ship` runs the gate (it skips step 7), nothing is printed. No warning
is added to `/ship` itself: the existing `context_nudge.py` hook already
alerts at 300k context and every 100k after.

### §2 A subagent writes and gates the plan (step 3)

Whenever step 3 would write a plan or run the plan gate, `/ship` no longer
does either itself. That is: no plan exists for the spec, or a plan exists
and `--verify-record` on it prints neither `ok:` nor
`decisions not approved` (the cases where step 3 runs the gate today). It
dispatches one **new** general-purpose subagent on the session's own model
(no `model` override), with no conversation, summary or other context, and
only this prompt (absolute paths):

> In the git worktree at `<feature worktree root>`, the approved spec is
> `<spec>` and its gate record is `<spec gate record>`. Existing plan:
> `<plan>` (or `none`).
>
> If the existing plan is `none`, write the implementation plan for the
> spec using the `superpowers:writing-plans` skill, saved as
> `docs/superpowers/plans/<YYYY-MM-DD>-<slug>.md`. Where the spec leaves a
> choice open, prefer one the spec, its ADRs or the existing code already
> imply. Answer every question under `## Plan questions` in the spec gate
> record in the task it affects (none if the section is missing). Add a
> `**Depends on:**` line under each task's `**Files:**` block: `none`, or
> the earlier tasks whose results it uses (`Task 1, Task 3`); a task whose
> only link to earlier tasks is shared files gets `none`. Do not write a
> new plan over an existing one; the plan gate's own fixes to it are
> expected.
>
> Then run the `claude-kit:plan-gate` skill on the plan, steps 1–6 only (do
> not run step 7 and do not ask anything). Do not commit and do not offer
> an execution choice. Return exactly three lines: `Plan: <repo-relative
> path>`, `Verdict: pass | pass-with-decisions | fail`, and `Record:
> <repo-relative path of the plan gate record>` (`Record: none` when the
> gate stopped at `P4-spec-gated` and wrote no record).

`<feature worktree root>` is the absolute path of the `/ship` feature
worktree from step 2 (never the main checkout), and `<spec>`,
`<spec gate record>` and `<plan>` are absolute paths inside it. The gate's
reviewer subagents are dispatched by this subagent, as subagents can
dispatch subagents.

`/ship` then checks, in that worktree, that the plan file exists, that its
`**Spec:**` line names the spec, and that the reported verdict matches the
record's `Verdict` line (or, for `Record: none`, that the plan exists and no
record was written). If a check fails, `/ship` deletes any plan file and
record that subagent created (never an existing plan it was given) and
dispatches the subagent once more with the same prompt; a second failure is
handled like any failed command (debugged, not a stop rule).

From there step 3 is unchanged: `/ship` acts on the verdict as today (the
`pass` path, 3a–3e for `pass-with-decisions`, the `fail` stop rule), reading
the Plan-introduced decisions and Open items from the record file, and
makes every commit itself.

### §3 Implementation always runs in subagents (step 4)

Step 4's choice after `parallel-plan.py waves` becomes:

- **The script exits non-zero:** write the `Ruling:` ledger line as today,
  then implement with `superpowers:subagent-driven-development` on the plan
  (still not a stop rule).
- **Every wave has one task:** `superpowers:subagent-driven-development`.
- **Otherwise:** `claude-kit:parallel-tasks` with `<plan>` as its argument,
  as today.

`superpowers:executing-plans` and `superpowers:test-driven-development` are
no longer invoked directly by step 4 (SDD's implementers work test-first;
this is rationale, and `ship.md` step 4 names neither skill).
`/ship`'s existing override applies to SDD as to every skill it invokes: no
question, menu or checkpoint inside SDD pauses the run; SDD's own stop
reasons that are not `/ship` stop rules are settled with a `Ruling:` line;
a ruling on an irreversible, destructive or security-sensitive action never
carries the action out unless the spec requires it: it declines the action
and records why.
SDD's closing `superpowers:finishing-a-development-branch` is not run:
step 11 does the clean-up. After each task SDD marks complete, the main
session runs the full test suite and lint from `CLAUDE.md` with quiet output
and confirms the task's commit is on the branch; a red suite is debugged
with `superpowers:systematic-debugging` before the next task. The Docker
baseline and labelling rules of step 4 are unchanged.

**`parallel-tasks` under `/ship`.** Every place where `parallel-tasks`
implements a task inline gains a caller condition. When the caller is
`/ship`, the task runs through SDD's task loop instead (one implementer
subagent, its task review and fix rounds, and the `Task N: complete` ledger
line) in the feature worktree. The places are:
- step 3's "One task" branch;
- step 3's failed-task fallback in a multi-task wave ("implement that task
  inline in the feature worktree from the merged HEAD");
- step 2's fallback when the script exits non-zero (the remaining tasks run
  one at a time through SDD's task loop, not `executing-plans`).

For any other caller (`/ship-fast` or a manual run) all three stay inline as
today. SDD and
`executing-plans` share one plan workspace and ledger, so the ledger that
`parallel-tasks` already sets up is the one SDD's loop writes to.
`parallel-tasks`' final whole-branch review is unchanged.

### §4 One final review (step 6)

Every step-4 path now ends with a fresh-context whole-branch review: SDD's
final review, or `parallel-tasks`' final review. Step 6 becomes:

- If step 4 ran its skill's final whole-branch review in this run, step 6
  does not run `superpowers:requesting-code-review`; the findings that
  review fixed are the review findings for the PR and the report.
- Otherwise (for example a resumed run that found every task already
  complete and did not reach a final review), step 6 runs as today:
  `requesting-code-review` on `origin/main..HEAD`, then
  `receiving-code-review`.

A finding that needs a scope, product or behaviour decision the spec does not
settle is still a stop rule, whichever review raised it. Step 12's "the
review findings you fixed" reads from whichever review ran.

### §5 Measuring a `/ship` run

`token-report.py --ship` lists, for each session in the project whose user
messages invoke `/ship` or `/claude-kit:ship` (a `<command-name>` tag of
`ship`, `/ship` or `/claude-kit:ship`), one row: session id (8 characters),
date, main-session cost, its subagents' cost (the session's
`<session id>/subagents/*.jsonl` files), total cost and peak main-session
context. Cost is cost-weighted tokens as defined in Purpose. Each API message counts
once: transcript records that share a `message.id` are counted once, in the
main transcript and in each subagent transcript. A last line
gives the median of each column. It reads transcripts only, with the
standard library only, like the rest of the script.

### ADR 0037

**`/ship`'s main session coordinates; subagents write the plan and the
code.** Context: a `/ship` run's tokens go mostly to its main session, whose
context grows through brainstorming, plan writing and inline implementation
and is re-read on every turn (median run 18.0M cost-weighted tokens, 391k
peak context, over 66 runs). Decision: the spec gate's approval message
sends the user to a fresh session for `/claude-kit:ship`; step 3 has a
fresh subagent write the plan and run the plan gate on it, while `/ship`
keeps acting on the verdict and making the commits; step 4 always implements through
`superpowers:subagent-driven-development` (or `claude-kit:parallel-tasks`,
whose one-task waves under `/ship` use SDD's task loop); step 6 reuses step
4's final review. Consequences: the main session holds the spec, the plan
path, verdicts and summaries; each task is built in a fresh context; each
task run through SDD gets a per-task review, while multi-task waves keep
`parallel-tasks`' plain subagents and its final review; subagent cost rises while main-session cost falls, so runs
are judged on total cost (`token-report.py --ship`). Amends ADR 0017 for
inline tasks under `/ship`. `/ship-fast` is not affected.

## Decisions

- **Fresh session:** the gate's approval message tells the user to `/clear`
  and run `/claude-kit:ship <path>`; no warning is added inside `/ship`.
- **Plan writer and gate:** one fresh subagent on the session's own model
  writes the plan and runs `claude-kit:plan-gate` steps 1–6, returning the
  plan path, verdict and record path; `/ship` keeps 3a–3e and the commits.
- **Implementation:** SDD when every wave has one task and for the
  script-failure fallback; `parallel-tasks` when any wave has more than one
  task, its inline paths using SDD's task loop under `/ship` only.
- **One final review:** step 6 runs its own review only when step 4 ran
  none.
- **`/ship-fast` out of scope;** `/ship-many` inherits through `/ship`.
- **Measurement:** `token-report.py --ship` (my call, so the post-merge
  evaluation below can be reproduced).

  and `/claude-kit:ship docs/superpowers/specs/`.

  - step 3 contains "general-purpose subagent", and its subagent prompt

  - outside that prompt, step 3 does not contain `superpowers:writing-plans`;
  - step 4 contains `superpowers:subagent-driven-development`,

  - step 6 contains the condition on step 4's final review and still names
    `superpowers:requesting-code-review` for the other case.

  fallback and the non-zero fallback each name `/ship` and
  `superpowers:subagent-driven-development`, and the inline case for other
  callers.
- `tests/test_token_report.py`: on a fixture project directory with one
  `/ship` session (two assistant turns with known usage, one of them
  repeated on a second record with the same `message.id`) and one subagent
  file, `--ship` prints a row with the expected main, subagent and total
  cost and peak context; a session without a `/ship` command is not listed.

## Success criteria

Agreed with the user before the work:

1. `pytest` passes, including the tests above.
2. `ruff check plugin tests` and `ruff format --check plugin tests` are
   clean.
3. The spec gate and the plan gate both pass for this change: `spec-lint.py --verify-record` prints `ok:` on the spec and on the plan.
4. `git grep -n "executing-plans" plugin/commands/ship.md` returns no match.

## Post-merge evaluation

Agreed with the user; checked after merge, not part of this change's PR. First
recompute the baseline: `token-report.py --ship` over the past `/ship` runs
(medians of total cost and peak main-session context). Then, on the next 3
real `/ship` runs, compare with it:

- median total cost per run at least 30% lower (subagents included);
- peak main-session context under 250k in each run;
- gate verdicts reached as before, CI green within the existing 3 attempts,
  no stop rule fired by the new steps, and no more Critical or Important
  final-review findings than in past runs.

A miss on cost or quality reopens the design.
